Specification checks

Section 6 of the Minimum Viable Specification for a Worldwide Agentic Web lists what an implementation should be able to demonstrate. This page says where Open Resolution Desk shows each item, and runs the four visible stops on small test networks.

Section 6 itemWhere and how it is shown
Publish a two-agent HOCON network and a manifest from an ordinary HTTPS web host.The desk's case network has two agents, a case assistant and a terms analyst (HOCON source, manifest), on GitHub Pages.
Load and run that network in a browser with the site's published default router and model; if BYOK is offered, also demonstrate the user-selected path.The checks on this page run with the router their manifests publish (the runtime's mock), with no key. The desk and the shops offer BYOK under each chat, tested with a local model.
Call an internal agent and at least one grounded capability through MCP or a registered local site action.On the case page, ask what a clause says: the case assistant calls the terms analyst, which reads the case through a site action. The Developer view shows the call.
After user approval, load an exact named network from a second origin and run it locally in the caller's browser.The desk loads the shop's representative network from ord-demo-shops.github.io after a consent card, and the shops load the desk's procedure guide. The Across sites panel lists each load.
When a user key is active, show that the second site never receives it and cannot change the caller's router.The Across sites panel names the model router as the only place the key goes. The model test records every request and finds the test key only in requests to the router. Peers run with the caller's router.
Show that private context is absent at the peer unless a named field is explicitly allowed.The page puts the customer's contact in private context, and the case network allows only case_ref downstream. The Across sites panel shows the fields passed to the shop's network: case_ref only.
Stop an invalid network, a composition cycle, an over-budget request, and a denied origin with visible errors.The four checks below, each on its own page: invalid network, composition cycle, over-budget request and denied origin.

The visible stops

This page runs the agentic-web browser runtime, unchanged, on a small test network. The runtime's built-in mock model calls each tool once, in order, so the check needs no key and gives the same result every time. It does not use a model key saved for this site.

  • Invalid network: The runtime fetches the broken network's manifest and definition, validates it, and refuses to run it.
  • Composition cycle: The runtime runs B, then refuses to run A again inside the same request.
  • Over-budget request: The runtime allows four remote calls per query and one call per peer.
  • Denied origin: The runtime asks before contacting the other origin.

Each test network is published like any other: a manifest, a network definition in JSON, and links.json. Another runtime can load the same files to check its own behaviour.

Check any site's public files

The repository includes tools/check_agentic_site.mjs, which reads a site's manifest, network definitions and links.json as a browser on another origin would, checks CORS and HTTPS, validates each network with the runtime's own parser and validator, and follows the peer networks they name. With Node.js 22 or newer:

node tools/check_agentic_site.mjs https://taronsung.github.io/open-resolution-desk/

It finds the same fault in the invalid-network check without a browser: run on https://taronsung.github.io/open-resolution-desk/spec-checks/invalid/, it follows the call to the broken network and reports two failures that name the missing tool ghost_agent.
